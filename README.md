# 古籍制版 · 字模工位管理

几册古籍陆续送到同一制版工位、共用外字字模。本服务管理分册用字与优先字库清单，
在每次“交印”时算出工位上字模的**增减单**：哪些字模要补备、哪些可以撤下。

## 业务规则

1. 上传**按优先顺序排列的字库清单**（CSV：`字库,版次,字模号,字`），文件顺序即优先级。
2. 上传**分册用字表**（CSV：`字`，每格可多字、可无表头）。
3. 每个字取**第一个收录它的字库**中的字模，按 **(字库, 版次, 字模号)** 识别字模。
4. 交印一册时**只更新该册**选用的字模；其余册沿用各自上次交印的清单（从未交印的册不参与共需）。
5. 比对交印前后**各册共需字模的并集**，生成增减单；只有最后一个使用某字模的册撤下它时，才出现“减”项。
6. **并发交印按生效次序逐单出单**：进程内互斥锁 + SQLite `BEGIN IMMEDIATE`/WAL/忙等待双重保证，
   每单提交前后都校验并集与各册 active 清单一致，不一致即回滚报错。
7. **重复确认复用原单**：
   - 带 `Idempotency-Key` 请求头：同键永远返回同一单；
   - 不带键：同册、同用字、解析目标与当前已交印清单完全相同（无变化）时，复用该册最近一单；
   - 按单号 `GET /api/orders/{单号}` 可原样重取，`.../download` 下载 CSV。
8. **缺字或保存失败时整笔回滚**，各册仍沿用原清单，不产生新单。
9. **清空工位**（`POST /api/reset`）：
   - 删除字库、分册、各册已交印清单与旧单内容；
   - 旧单号重取 JSON 或下载 CSV 一律 `404 单据不存在`，绝不会下载到清空后新出的单；
   - 旧幂等键留下墓碑，重试返回 `409 该笔交印已清空`，不出单、不改动共需清单；
   - 单号进入新世代 `MO日期-G{次数}-{序号}`，序号从 1 重新计，当天重新出首单也不沿用旧号；
   - 与交印共用同一把互斥锁和 `BEGIN IMMEDIATE` 事务，重叠时按生效次序逐笔处理；
   - 清空失败整笔回滚，原单仍可查询、原键仍可复用。
10. **持久化**：清空事件、世代与幂等键墓碑都写在 SQLite 中，服务重启后依然区分
    清空前后的单号与键；旧版本数据库启动时自动补列升级，库内既有单据照常查询和复用。

## 目录

```
app/            FastAPI 应用（database/parsers/service/main）
web/index.html  单页操作界面（上传、交印、重取、下载、清空、状态总览）
samples/        网页与接口可直接使用的样例 CSV（1 份字库清单 + 2 册用字表）
tests/          pytest 端到端测试（19 个用例：业务规则 + 清空/重取/重试 + 升级/重启）

```

## Docker Compose 启动

```bash
docker compose up --build
# 打开 http://localhost:8000/
# SQLite 数据持久化在命名卷 matrix-data -> /data/matrix.db
```

页面上可直接下载 `/samples/` 下的样例文件，按 ① 字库清单 → ② 用字表 → ③ 交印 的顺序操作。
“⑤ 清空工位”演示清空、重取与重试：交印后单号会自动填入重取框，清空后旧单号取 JSON /
下载 CSV 均提示“单据不存在”，重新上传再交印得到带 `G{n}` 的新号，用旧幂等键重试则提示
“该笔交印已清空”。

## 本地运行（无 Docker 时）

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
# 测试
pip install -r requirements-dev.txt
pytest -q
```

## HTTP 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/libraries` |  multipart 上传字库清单 CSV，全量替换当前生效清单 |
| POST | `/api/volumes/{册名}/chars` | 上传该册用字表 CSV，全量替换用字 |
| POST | `/api/volumes/{册名}/submit` | 交印并出增减单；可选 `Idempotency-Key` |
| GET  | `/api/orders?volume=册名` | 按生效次序列出单据 |
| GET  | `/api/orders/{单号}` | 按单号原样重取 JSON |
| GET  | `/api/orders/{单号}/download` | 下载增减单 CSV（带 BOM，Excel 直开） |
| GET  | `/api/state` | 当前字库、各册用字/已交印字模、共需并集、单号世代与清空记录 |
| POST | `/api/reset` | 清空工位（字库/分册/旧单内容）；可选 `X-Fail-Clear: 1` 演练失败回滚 |
| GET  | `/docs` | Swagger 交互文档 |

增减单 JSON 关键字段：`added` / `removed`（共需池层面的增减，含字库/版次/字模号/字）、
`pool_before` / `pool_after`（交印前后共需并集）、`volume_before` / `volume_after`（该册清单）、
`seq` / `generation`（生效序号与清空世代）。

清空相关响应：

- 旧单号：`GET /api/orders/{单号}` 与 `.../download` 均 `404`，`type=OrderNotFoundError`，文案“单据不存在”；
- 旧幂等键重试：`409`，`type=ClearedIdempotencyKeyError`，文案“该笔交印已清空”，不产生单据；
- 清空接口返回 `clear_id` / `removed_orders` / `removed_idempotency_keys` / `next_generation`。

## 数据模型（SQLite）

- `libraries`（字库+版次，优先级，current 标记）、`glyphs`（字库内字模号→字）
- `volumes` / `volume_chars`（册与用字，保留用字顺序）
- `active_matrices`（各册**上次交印**生效的字模清单）
- `submit_seq`（全局生效序号）、`orders`（单号、序号、幂等键、指纹、整单 JSON 快照、`generation` 世代）
- `clears`（每次清空一条，`clear_id` 即当前世代号，重启后据此继续区分单号）
- `cleared_idempotency_keys`（已清空旧单的幂等键墓碑，重试据此拒绝）

旧版本数据库启动时由 `init_db()` 自动补列升级（给 `orders` 增加 `generation`，默认 0），
既有单据不改写、照常查询和复用。

## 做完了什么 / 验过什么 / 未完成

### 已完成

- FastAPI + SQLite 全量功能：字库/用字上传、优先选库、交印出单、单据重取与 CSV 下载、状态总览、单页网页与样例数据。
- 并发串行化（应用锁 + 数据库立即事务 + WAL + 30s 忙等待）、幂等键与无键判重、缺字/保存失败回滚。
- **清空工位语义**：删除字库/分册/旧单内容；旧单号 JSON 与 CSV 均 404；旧幂等键返回 409
  且不出单、不改共需清单；清空后单号进入 `G{n}` 新世代（序号从 1 重计）；
  交印与清空共用互斥锁和立即事务，重叠时按生效次序线性化；清空失败整笔回滚。
- **持久化与升级**：清空事件、世代、幂等键墓碑均落 SQLite；重启后继续区分清空前后；
  旧库启动时自动补 `orders.generation` 等结构，无需重建，既有单据照常查询/复用。
- Dockerfile 与 docker-compose（命名卷持久化、健康检查）。

### 已验证（本环境实际运行）

- `pytest` 19 个用例全部通过（连续多轮无偶发失败），其中新增用例覆盖：
  清空后旧单 JSON/CSV 均 404、当天新首单号不同于旧号、旧键重试 409 且工位状态不变、
  多次清空后旧键仍被拒绝、清空失败后原单可查可复用、交印与清空并发线性化、
  重启后旧单仍 404 / 新单仍 200 / 旧键仍 409、旧版 SQLite 就地升级后既有单可查可复用再清空。
- 原有业务用例继续通过，含题目指定的**两册先后弃用同一字模**：
  甲先弃时乙仍需 → 无减单；乙再弃（最后使用者）→ 减单含该字模；每单 pool 与各册并集逐单一致。
- 真实启动 uvicorn（非 TestClient）用样例 CSV 冒烟：上传→两册交印（`…-000001/2`）→
  清空→旧单 JSON/CSV 均 404→旧键 409→重新上传交印得 `…-G1-000001`→
  重启进程后旧单仍 404、新单仍 200、旧键仍 409、新交印仍复用 `G1-000001`。
- 并发交印、编码回退（UTF-8 BOM / GB18030）、无表头用字表、坏表头 400、
  未知册/单号 404、保存失败回滚。

### 未完成 / 限制

- 本环境没有 Docker 守护进程，`docker compose up --build` 仅做了文件级准备，未实机构建运行；
  Dockerfile 基于 `python:3.11-slim` 与已验证的依赖版本，逻辑上与本地运行一致。
  本地已用同一条 uvicorn 启动命令实跑验证。
- 应用级互斥锁只在单进程内生效；多进程/多副本部署时依赖 SQLite 的立即事务与忙等待兜底，
  建议仍以单副本 + 卷持久化方式运行（compose 默认即如此）。
- 字库清单替换为管理操作：替换后已交印册仍锁定在旧字模（保留历史可追溯），
  重新交印时才按新清单解析；未对替换操作加单独权限控制。
- 没有账号/鉴权与操作审计（题目未要求）；`/api/reset` 仅适用于演示环境。
- 清空是“硬删除旧单内容 + 保留键墓碑”，清空事件只记录次数与时间（不保留旧单明细，
  以满足“旧单内容删除、旧单号不可再取”的要求）；如需审计，可另加外部日志。
